# مسار الإصدار الآمن للنظام

## البيئات

- Development: فروع التطوير، ولا تحتوي بيانات عملاء حقيقية.
- Staging: مشروع Supabase مستقل، تُشغّل عليه جميع الترحيلات والاختبارات الوظيفية والمالية.
- Production: مشروع العملاء، ولا يستقبل إلا إصداراً اجتاز الاختبارات والمراجعة.

## بوابات النشر

1. كل تعديل يبدأ بفرع مستقل.
2. يجب أن ينجح TypeScript والاختبارات والبناء وSupabase migration reset على قاعدة محلية نظيفة.
3. يجب اختبار migrations على Staging ببيانات اصطناعية، وكذلك اختبار الترقية من نسخة قاعدة سابقة.
4. لا تُدمج التغييرات المالية أو الأمنية قبل مراجعة فرق SQL وRLS وRPC grants.
5. تُنشر واجهة التطبيق بعد اجتياز الاختبارات، بينما تُطبّق migrations الإنتاجية عبر مسار إصدار مضبوط وبعد أخذ نسخة احتياطية والتحقق منها.
6. تُستخدم تغييرات قاعدة البيانات المتوافقة مع الإصدار السابق: إضافة، ترحيل، ثم إزالة القديم في إصدار لاحق.
7. تُفعّل الميزات الجديدة تدريجياً عبر Feature Flags، ويمكن إيقافها دون الرجوع عن بقية الإصدار.
8. بعد النشر تُراقب أخطاء التطبيق وقاعدة البيانات، وزمن الاستجابة، واستهلاك التخزين والاتصالات.

## الاستعادة

- احتفظ بنسخة احتياطية قبل تغييرات المخطط الحساسة.
- اختبر الاستعادة في مشروع منفصل، ولا تكتفِ بوجود نسخة احتياطية.
- تغييرات التطبيق يمكن الرجوع عنها بإصدار سابق إذا بقي المخطط متوافقاً.
- لا تعتمد على rollback آلي لترحيلات البيانات؛ استخدم forward-fix عندما تكون عكسية التغيير غير آمنة.

## ملاحظة CI في هذا المستودع

ملف .github/workflows/ci.yml يشغّل فحوصات push على الفروع main وfeature/**، بينما فحص pull_request مضبوط حالياً على main فقط. لذلك يجب أن تكون فروع الإصلاح التي نريد لها فحص push ضمن feature/**، ويجب عدم اعتبار عدم ظهور فحص PR على فرع أساس آخر دليلاً على نجاحه.
