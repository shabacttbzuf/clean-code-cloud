### 1) سلامة البيع — إصلاح برمجي مضاف

وجدنا في `public.create_sale_with_customer` أن فحص `jsonb_typeof(_items) <> 'array'` لا يرفض `NULL` بصورة مضمونة؛ فشرط PL/pgSQL قد يصبح NULL بدلاً من TRUE، ما يسمح بتجاوز شرط التحقق ثم إنشاء فاتورة دون بنود.

أضيف ترحيل `20261119010000_pre_sale_security_performance_hardening.sql` ويقوم بـ:
- رفض `NULL` وأي نوع JSON غير array قبل استدعاء `jsonb_array_length`.
- رفض المصفوفة الفارغة والمصفوفات التي تتجاوز 300 بند.
- الإبقاء على فحص الصلاحية والفرع والعميل وحد الائتمان وتسجيل `cost_price_snapshot` من سعر التكلفة الفعلي في قاعدة البيانات.
- عدم تعديل أي فاتورة أو حركة مخزون قديمة.

أضيف اختبار انحدار آلي يتحقق من ترتيب الحماية ومنع التراجع.

### 3) كلمات المرور المسربة — تم تحديد الإعداد ومتطلب تفعيله

Security Advisor يؤكد أن Leaked Password Protection غير مفعّل. توثيق Supabase الحالي يذكر أن هذه الميزة متاحة على خطة Pro وما فوق، وتُضبط من Authentication → Auth settings، وليس عبر SQL أو ترحيل PostgreSQL.

لا تتوفر في اتصال المشروع الحالي أداة إدارة لإعدادات Auth أو Management API token؛ لذلك لم نزعم تفعيلها ولم نغيّر إعدادات الدخول. قبل استقبال مستخدمين تجاريين:
1. تأكد أن خطة Supabase هي Pro أو أعلى.
2. افتح إعدادات Authentication / Auth Providers.
3. فعّل منع كلمات المرور المسرّبة، واجعل الحد الأدنى 10 أحرف على الأقل، واختر متطلبات قوية لكلمات المرور.
4. اختبر إنشاء مستخدم بكلمة مرور مسرّبة (يجب رفضها) وكلمة مرور قوية (يجب قبولها).

المرجع: https://supabase.com/docs/guides/auth/password-security

أضيف اختبار آلي ضمن `npm test` / `bun run test`، واختبار pgTAP ينفذ على PostgreSQL المحلي بعد تطبيق الترحيلات للتحقق من تعريف الدالة الفعلي واختفاء السياسات التسع. سيشغّل CI أيضاً:

- اختبارات Node الحالية والجديدة.
- Production build.
- بدء Supabase محلياً.
- تطبيق كل الترحيلات على قاعدة محلية فارغة.
- تشغيل اختبارات PostgreSQL عبر `supabase test db` (pgTAP).

مصفوفة اختبارات القبول المطلوبة على Staging مستقل قبل البيع:
1. بيع نقدي بمنتج واحد وعدة منتجات، والتحقق من الفاتورة والدفع وخصم المخزون.
2. بيع آجل وجزئي، والتحقق من حد ائتمان العميل ولقطة تكلفة الصنف.
3. تحصيل جزئي وكامل مع تكرار idempotency key، والتأكد من عدم مضاعفة المبلغ.
4. مرتجع جزئي وكامل مع restock مفعّل/معطّل، والتأكد من حركة المخزون والقيود المالية ورصيد الصندوق.
5. مرتجع مشتريات والتحقق من عدم تجاوز كمية الشراء الأصلية.
6. إغلاق الصندوق بعد المبيعات والمرتجعات والتحصيلات ومطابقة النقد المتوقع.
7. مستخدمان من شركتين مختلفتين، ومدير شركة، ومدير فرع، وكاشير؛ اختبار القراءة والإنشاء والتعديل والحذف والتقارير لكل نطاق.
8. اختبار تزامن بيع آخر كمية، وتكرار التحصيل، ومحاولتي إرجاع متزامنتين.
9. الموارد البشرية: حضور، إجازة، مسير راتب، مكافأة وخصم، مع عزل الشركة والفرع.
10. استعادة نسخة احتياطية إلى مشروع منفصل والتحقق من التطبيق والبيانات.

هذه المصفوفة موثقة كخطة قبول، وليست ادعاءً بأن اختبارات واجهة المستخدم الحقيقية أو اختبار التزامن قد نُفذت بالفعل. لا توجد بيئة Staging مستقلة مؤكدة في الاتصال الحالي.
