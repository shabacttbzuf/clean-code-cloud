## الأسباب التي كشفها تحليل البناء

1. استيراد ملفات الخطوط العامة `@fontsource/<font>/<weight>.css` أنتج 66 ملف خط، بما فيها مجموعات Greek وCyrillic وVietnamese وLatin Extended غير لازمة لواجهة عربية أولاً.
2. حزمة الرسوم البيانية كبيرة، لكن تحميلها مفصول بالفعل باستخدام `React.lazy` و`IntersectionObserver`، لذلك لا ينبغي دمجها في الحزمة الأولية.
3. محرك PDF كبير. في خط الأساس كان `jspdf` مستورداً أعلى `invoice-pdf.ts`، لذلك كان يُحمّل عند تحميل مسار نقطة البيع أو تفاصيل الفاتورة، حتى قبل الضغط على زر PDF. التعديل الحالي ينقل استيراد المحرك إلى داخل دالة إنشاء الملف، ليُحمّل فقط بعد طلب التصدير صراحةً.
4. لا يكفي مجموع أحجام جميع ملفات JS لتحديد حجم أول شاشة. يلزم تقرير موارد/trace من متصفح لقياس الطلبات الحرجة فعلياً.

## التغيير المعتمد بعد خط الأساس

- حصر Cairo في مجموعة Arabic للأوزان 400/500/600/700.
- حصر Inter في مجموعة Latin للأوزان 400/500/600.
- لا تغيير في عائلة الخطوط أو الأوزان أو مظهر الواجهة المقصود.
- أضيف اختبار يمنع العودة إلى استيراد ملفات الخطوط العامة لكل المجموعات.

## شروط المقارنة بعد التعديل

يجب مقارنة سجل بناء جديد على نفس الفرع، ونفس workflow، ونفس إصدار الاعتماديات، ومقارنة:
- عدد ملفات الخطوط الناتجة ومجموع أحجامها.
- عدد ملفات JavaScript ومجموع raw/gzip، مع فصل الحزم المؤجلة عن موارد البداية متى أمكن.
- LCP وINP وCLS من تشغيل متصفح موثق على المسارات نفسها، مع بيئة مصادقة وبيانات اختبار ثابتة.
- تشغيل محاكاة هاتف متوسط (CPU/network throttling) بنفس الإعدادات قبل وبعد.

لا تُعلن المهمة مكتملة قبل توفر قياسات Core Web Vitals قبل/بعد للصفحات الحرجة، ونجاح TypeScript والاختبارات وProduction Build.
