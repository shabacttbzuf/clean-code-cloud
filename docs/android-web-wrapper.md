# تغليف نظام الويب كتطبيق Android

## القرار المعماري

سيبقى نظام إدارة المطاعم تطبيق ويب واحداً (React + TanStack Start) ومصدراً وحيداً للواجهات وقواعد العمل. لن ننشئ تطبيق Android مستقلاً أو نعيد كتابة الشاشات بـ Kotlin/Compose.

عند جاهزية رابط النشر النهائي، يكون التغليف باستخدام **Capacitor Android** كحاوية WebView للتطبيق المنشور، مع إبقاء واجهات الويب وعملياتها مشتركة بين المتصفح وAndroid. وتُستخدم PWA وService Worker لتجهيز الموارد ودعم الفتح بعد الزيارة الأولى.

## لماذا لم نضف مشروع Android الآن؟

- المستودع لا يحتوي حالياً على نطاق نشر إنتاجي موثوق يمكن ربط حاوية Android به.
- المشروع مبني على TanStack Start ويعتمد على خادم ويب؛ لا يجوز افتراض أن مجلد build ثابت يصلح وحده كتطبيق محلي.
- إضافة عنوان نشر افتراضي أو إعداد Capacitor قبل تثبيت النطاق قد ينتج APK يفتح عنواناً خاطئاً أو يتعطل عند الإطلاق.
- يلزم اختبار Service Worker والتخزين المحلي داخل Android WebView قبل اعتماد APK.

## خطوات التغليف بعد تثبيت رابط الإنتاج

1. إضافة Capacitor Core وCLI وAndroid إلى المشروع وتثبيت إصدارات متوافقة.
2. إعداد معرف Android واسم التطبيق والأيقونات وشاشة البداية.
3. ربط WebView بعنوان الإنتاج HTTPS المعتمد، دون إعادة بناء الواجهات.
4. تفعيل تكامل الروابط العميقة والتنقل والعودة وزر الرجوع.
5. اختبار PWA/Service Worker وIndexedDB والجلسات داخل Android WebView.
6. اختبار تسجيل الدخول والخروج وانتهاء الجلسة وانقطاع الشبكة والعودة إليها.
7. بناء APK تجريبي ثم اختبار التحديثات قبل إصدار الإنتاج.

## حدود العمل دون اتصال

تخزين واجهة الويب لا يعني أن Supabase أو تسجيل الدخول أو كل عمليات المطعم تعمل دون اتصال. البيانات المحلية ستقتصر على بيانات مسموح بها ومحددة النطاق، وتبقى صلاحيات الشركة والفرع والتحقق من الخادم إلزامية عند المزامنة. لا تُخزّن كلمات المرور أو مفاتيح الخدمة أو استجابات المصادقة في Cache Storage.
