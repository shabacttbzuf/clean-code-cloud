# إعادة إنشاء قاعدة بيانات المشروع

## الحالة الحالية

هذا الدليل يشرح مسار إعادة الإنشاء الآمن. لا تعتبر قاعدة البيانات جاهزة للإنشاء من الصفر حتى تكتمل مراجعة جميع ملفات `supabase/migrations` واختبارها على مشروع Supabase تجريبي فارغ.

**لا تنفّذ هذا الإجراء على مشروع الإنتاج أو على مشروع يحتوي بيانات تريد الاحتفاظ بها.**

## مصدر مخطط قاعدة البيانات

- ملفات SQL التاريخية في `supabase/migrations/` هي سجل التغييرات الأساسي.
- لا تعدّل ترحيلاً قديماً سبق تطبيقه؛ أضف ترحيلاً جديداً فقط.
- `src/integrations/supabase/types.ts` ملف أنواع مولّد، وليس بديلاً عن مخطط SQL.
- `drizzle/schema.ts` في النسخة الحالية معلن صراحة أنه فارغ عمداً؛ لذلك لا يجوز اعتباره مخطط قاعدة البيانات أو تشغيل Drizzle باعتباره مصدر الحقيقة.\n- يوجد ترحيل Drizzle قديم في `drizzle/migrations/0000_scope_permission_visibility.sql`. نُقلت قواعده إلى ترحيل Supabase إضافي داخل `supabase/migrations/` حتى لا تُهمل عند إنشاء قاعدة جديدة. لا تشغّل ملف Drizzle القديم مرة ثانية بعد تشغيل سلسلة Supabase.

## خطوات الإنشاء بعد اكتمال تدقيق سلسلة الترحيلات

1. أنشئ مشروع Supabase جديداً فارغاً.
2. احتفظ بمعرّف المشروع الجديد ورابطه ومفاتيحه في إعدادات النشر السرية، ولا تضع مفتاح `service_role` في Git أو في المتصفح.
3. ثبّت Supabase CLI وسجّل الدخول.
4. اربط مجلد المشروع بالمشروع الجديد:
   `supabase link --project-ref <NEW_PROJECT_REF>`
5. بعد التحقق من جميع ملفات الترحيل وترتيبها، نفّذ:
   `supabase db push`
6. حدّث متغيرات البيئة في منصة الاستضافة:
   - `SUPABASE_URL`
   - `SUPABASE_PUBLISHABLE_KEY`
   - `VITE_SUPABASE_URL`
   - `VITE_SUPABASE_PUBLISHABLE_KEY`
   - `SUPABASE_SERVICE_ROLE_KEY` (خادمي فقط، سري)
   - `INITIAL_SUPER_OWNER_USER_ID` (خادمي فقط، مؤقت لإعداد المالك الرئيسي الأول)
7. أنشئ حساب المستخدم الأول، ثم ضع UUID الخاص به في `INITIAL_SUPER_OWNER_USER_ID`، واستدعِ إجراء تهيئة المالك الرئيسي مرة واحدة.
8. بعد نجاح التهيئة، احذف `INITIAL_SUPER_OWNER_USER_ID` من بيئة التشغيل.
9. حدّث أنواع Supabase من قاعدة البيانات الجديدة، ثم شغّل فحوص البناء والاختبارات.

## تنبيه بشأن ملف شامل واحد

لا تجمع ملفات SQL القديمة آلياً في ملف واحد قبل فحص الاعتماديات والـ triggers والـ policies والـ functions. قد ينتج عن ذلك تكرار أنواع أو جداول أو سياسات، وقد يتغير ترتيب التنفيذ. الخطة المعتمدة هي اختبار سلسلة الترحيلات كاملة على قاعدة فارغة أولاً، ثم إنشاء ملف baseline موحّد موثوق إذا كان مطلوباً فعلاً، مع إبقاء السجل الأصلي محفوظاً.

## ملف الهجرة الشامل

- الملف المجمع: `supabase/COMPLETE_DATABASE.sql`
- قائمة الملفات وترتيبها: `supabase/MIGRATION_MANIFEST.md`
- عدد الترحيلات الحالية في السلسلة: 31 (20 تاريخية + 11 إصلاحية جديدة).

الملف المجمع Snapshot مرجعي/لإعادة البناء من قاعدة فارغة. المسار الموصى به يبقى `supabase db push` لأنه يسجل كل ترحيل بصورة صحيحة. لا تستخدم الملف المجمع يدوياً ثم تشغّل `db push` على القاعدة نفسها.

## ما لم يتم التحقق منه بعد

- لم يتم الاتصال بأي قاعدة Supabase.
- لم يتم تنفيذ أي ترحيل على قاعدة حية أو جديدة.
- لم يتم اختبار سلسلة الترحيلات على قاعدة فارغة بعد.
- لا تعتمد على هذا الدليل وحده كإذن لتشغيل الترحيلات قبل اكتمال التدقيق.
