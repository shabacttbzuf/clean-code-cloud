## ملاحظات أمنية ذات أولوية

### P0 — مراجعة سياسات RLS المتعددة قبل الإطلاق

وجود عدة سياسات permissive على الجدول والعملية نفسها يعني أن PostgreSQL قد يجمع شروطها بمنطق OR. لذلك فإن إضافة سياسة permission_gate لا تكفي وحدها إذا بقيت سياسة قديمة أوسع تسمح بالعملية.

تم رصد سياسات ALL قديمة في جداول تشغيلية مثل attendance وemployees وpayroll_items وغيرها، إلى جانب سياسات granular حديثة. يجب فحص كل جدول/عملية على حدة، والتحقق من أن:
1. شرط صلاحية العملية مطلوب فعلياً.
2. شرط عزل tenant/company/branch مطلوب فعلياً.
3. صلاحيات المنع الفردية (explicit deny overrides) لا يمكن تجاوزها بسياسة قديمة.
4. المستخدم لا يستطيع تغيير tenant_id أو branch_id أو ربط سجل بسجل من شركة أخرى.

لا تُحذف السياسات القديمة بالجملة. يجب بناء مصفوفة لكل جدول ولكل عملية SELECT/INSERT/UPDATE/DELETE، ثم دمج شروط الصلاحية والنطاق في سياسة موثوقة أو استخدام سياسات RESTRICTIVE عند ملاءمتها، واختبار الأدوار قبل النشر.

### P1 — SECURITY DEFINER

تم العثور على 26 دالة SECURITY DEFINER في schema public. دوال has_permission وis_super_owner وget_my_permissions تمت مراجعة تعريفاتها:
- has_permission يتحقق من auth.uid() ومن أن user_id يطابق المستخدم الحالي، ويحدد search_path صراحة.
- is_super_owner يتحقق من تطابق هوية المستخدم مع auth.uid().
- get_my_permissions يتحقق من عضوية المستخدم في tenant قبل إرجاع الصلاحيات.

هذه نتائج إيجابية لهذه الدوال فقط، ولا تعتبر مراجعة مكتملة لبقية الدوال الـ23. يلزم جرد كامل للمدخلات، التحقق من التفويض، search_path، execute grants، وأثر كل دالة على المال والمخزون.

### P1 — إعدادات Auth

حماية كلمات المرور المسربة غير مفعّلة وفق آخر Security Advisor. يجب تفعيلها بعد مراجعة إعدادات Auth وتأثيرها على تسجيل المستخدمين، ثم اختبار تسجيل الدخول وتغيير كلمة المرور.

### P1 — تدقيق عمليات المال والمخزون

لا توجد حتى الآن أدلة كافية على اختبار شامل end-to-end لعمليات:
- البيع النقدي والآجل.
- التحصيل الجزئي والكامل.
- المرتجعات والإلغاءات.
- الشراء وسداد الموردين ومرتجعات الشراء.
- ترحيل المخزون وتكلفة البضاعة المباعة.
- جلسات الصندوق والإغلاق والتسوية.
- الرواتب والاستحقاقات والخصومات.

يجب تنفيذ هذه الاختبارات في بيئة معزولة فقط، مع assertions على أرصدة الحسابات وحركات المخزون وسجلات التدقيق. لا تنفذ معاملات اختبار على الإنتاج.

## الأداء والموثوقية

- راجع 122 مجموعة/ملاحظة تعدد سياسات permissive قبل أي تحسين آلي.
- لا تحذف 27 فهرساً مصنفاً غير مستخدم دون قياس وخطة rollback.
- اختبر الاستعلامات الأكثر استخداماً مع أحجام بيانات واقعية وخطط EXPLAIN (ANALYZE, BUFFERS) في بيئة اختبار.
- نفّذ اختبار تزامن على الكاشير والمخزون والتحصيلات؛ يجب أن تمنع المعاملات الذرية البيع المكرر أو المخزون السالب غير المقصود.
- وثّق النسخ الاحتياطي، احتفاظ النسخ، RPO/RTO، واختبر الاستعادة إلى مشروع منفصل قبل استقبال بيانات العملاء.

## النشر التجاري والتحديث دون تعطيل العملاء

البنية المستهدفة:
1. Development: تطوير الفروع والميزات.
2. Staging: مشروع Supabase منفصل وبيانات اختبار اصطناعية، مع تشغيل migrations والاختبارات.
3. Production: مشروع الإنتاج وبيانات العملاء الحقيقية.

قواعد الإصدار:
- لا تطبق migrations يدوياً على الإنتاج من جهاز المطور.
- كل تغيير قاعدة بيانات يأتي بملف migration مرقّم ومراجع، ويُختبر على قاعدة نظيفة وعلى نسخة تمثيلية من البيانات.
- استخدم تغييرات متوافقة مع الإصدار السابق (Expand → Migrate → Contract).
- استخدم feature flags للميزات غير الجاهزة أو التفعيل التدريجي لكل شركة.
- انشر إصداراً قابلاً للتراجع، مع خطة rollback للتطبيق وخطة forward-fix للبيانات.
- لا تدمج PR #2 أو PR #3 قبل مراجعة الاعتماد بينهما ونجاح جميع فحوصات CI والمراجعة الوظيفية.

## شروط اعتماد الإصدار للبيع

- لا توجد ثغرات عزل بين الشركات والفروع.
- لا يمكن تجاوز الصلاحيات الفردية أو صلاحيات الأدوار.
- مراجعة جميع SECURITY DEFINER وRPC grants.
- اختبارات مالية ومخزون ناجحة على Staging.
- اختبارات متزامنة ناجحة.
- استعادة نسخة احتياطية مجرّبة.
- لا أخطاء حرجة في سجلات المتصفح أو الخادم.
- قياس التكلفة والسعة لكل عميل، وخطة ترقية Supabase قبل التشغيل التجاري.
- مراقبة الأخطاء والأداء والتنبيهات، وخطة استجابة للحوادث.
