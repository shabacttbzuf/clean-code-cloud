# نظام إدارة المطاعم والمؤسسات والفروع

نظام ويب عربي RTL لإدارة أعمال متعددة المؤسسات والفروع، مبني على **React 19 + TanStack Start + TypeScript + Tailwind CSS 4 + Supabase PostgreSQL/Auth/RLS**.

المستودع يحتوي التطبيق الحالي، وملفات قاعدة البيانات، والترحيلات المتسلسلة، واختبارات الحماية والبناء.

## الوظائف الحالية

- **المؤسسات والفروع:** إنشاء المؤسسات، إدارة الفروع، وربط المستخدمين بأدوار ونطاقات فروع.
- **المستخدمون والصلاحيات:** أدوار أساسية وأدوار مخصصة، مع منع منح صلاحيات المالك أو المدير من قبل غير المخولين.
- **المنتجات والمخزون:** المنتجات والتصنيفات، أرصدة الفروع، حركات المخزون، والاستلام والتسويات.
- **نقطة البيع:** فواتير بيع ذرّية، احتساب الأسعار والضرائب والخصومات من قاعدة البيانات، وربط كل عملية بجلسة صندوق.
- **المشتريات:** فواتير شراء واستلام مخزون وتسجيل المورد والفرع.
- **الصندوق:** فتح وإغلاق الجلسات، احتساب الرصيد المتوقع من المدفوعات النقدية والمرتجعات النقدية.
- **المرتجعات:** مرتجعات جزئية أو كاملة لفواتير البيع، ومرتجعات للموردين، مع حفظ سجل مستقل وعدم حذف الفواتير الأصلية، وتحويل حالة فاتورة الشراء إلى «مرتجعة بالكامل» بعد رد كل الكميات.
- **الموارد البشرية:** بيانات الموظفين، الحضور والإجازات والرواتب.
- **الإدارة والتقارير:** المصروفات، لوحة المؤشرات، التقارير، الإشعارات، وسجل التدقيق.

## ضوابط المحاسبة والمخزون

- لا يسمح بحذف أو تعديل السجلات المالية مباشرة من عميل المتصفح؛ العمليات المالية تمر عبر دوال قاعدة بيانات محمية.
- كل عملية بيع تحفظ تكلفة المنتج وقت البيع في `cost_price_snapshot` حتى لا تتغير ربحية الفواتير القديمة عند تعديل تكلفة المنتج.
- لا يمكن إرجاع كمية أكبر من الكمية المباعة أو المشتراة.
- إرجاع صنف إلى المخزون يمر عبر حركة مخزون مرتبطة برقم المرتجع، ولا يسمح بأن يصبح رصيد المخزون سالباً.
- لا يمكن إصدار مرتجع نقدي يتجاوز الرصيد النقدي المتاح في جلسة الصندوق.
- رد البطاقة أو التحويل يسجل في النظام كعملية مرتجع، لكن تنفيذ التحويل البنكي أو رد البطاقة الفعلي يتم خارج التطبيق حالياً.
- مرتجع المورد يحفظ قيمته ويعكس المخزون، لكن تسوية رصيد المورد أو رد المبلغ نقدياً ليست مفعلة كدفتر حسابات موردين مستقل حتى الآن.

## الأمان وعزل المؤسسات والفروع

- تفعيل RLS على الجداول الجديدة، وسياسات القراءة محددة بالمؤسسة والفرع.
- تحقق قاعدة البيانات من تطابق المؤسسة بين السجل المرجعي والسجل الذي يشير إليه، بما في ذلك العلاقات التي لا تملك مفتاحاً أجنبياً تقليدياً.
- منع نقل السجلات بين المؤسسات بعد إنشائها، مع السماح بربط ملف المستخدم بمؤسسته عند التهيئة الأولى.
- التحقق من عضوية المستخدم عند تسجيله كمنفذ للعملية أو مستلم للإشعار.
- صلاحيات تعديل السجلات المالية والصلاحيات الإدارية محصورة في دوال محمية.
- دوال `SECURITY DEFINER` تضبط `search_path`، والدوال التي تتطلب صلاحية خدمة لا تمنح للمستخدم العادي.
- مخطط `private` مخصص للدوال الداخلية ولا ينبغي إضافته إلى مخططات Data API المكشوفة.
- صلاحيات الجداول الجديدة محدودة؛ لا يحصل `anon` على وصول إلى سجلات المرتجعات.

## قاعدة البيانات والترحيلات

- عدد ملفات الترحيل المتسلسلة حالياً: **53 ملفاً** داخل `supabase/migrations/`.
- `supabase/MIGRATION_MANIFEST.md` يسرد الترحيلات بالترتيب.
- `supabase/COMPLETE_DATABASE.sql` نسخة مجمعة تحتوي كل ترحيل مرة واحدة وبنفس الترتيب.
- لا تعدّل ترحيلاً سبق تطبيقه؛ أنشئ ملف ترحيل جديداً برقم وتاريخ لاحقين.
- لتطبيق الترحيلات على قاعدة محلية نظيفة استخدم `supabase db reset --local`.
- لا تشغّل `COMPLETE_DATABASE.sql` فوق قاعدة بيانات قائمة؛ استخدم نظام الترحيلات لتجنب تكرار التغييرات.

## المتطلبات والتشغيل المحلي

المتطلبات:
- Bun (الموصى به، ويستخدمه CI).
- Supabase CLI عند الحاجة إلى تشغيل قاعدة محلية.
- مشروع Supabase وبيانات اتصال صالحة.

1. انسخ ملف البيئة النموذجي:

```bash
cp .env.example .env.local
```

2. املأ القيم التالية من إعدادات مشروع Supabase:
   - `VITE_SUPABASE_URL`
   - `VITE_SUPABASE_PUBLISHABLE_KEY`
   - `VITE_SUPABASE_PROJECT_ID`
   - `SUPABASE_URL`
   - `SUPABASE_PUBLISHABLE_KEY`

3. وظائف الخادم الإدارية التي تحتاج صلاحية مرتفعة تتطلب `SUPABASE_SERVICE_ROLE_KEY` في بيئة الخادم فقط. لا تضع هذا المفتاح في متغير يبدأ بـ `VITE_`، ولا ترسله إلى المتصفح، ولا ترفعه إلى GitHub. احفظ القيم السرية في `.env.local` (وهو مستثنى من Git). متغير `INITIAL_SUPER_OWNER_USER_ID` مؤقت للتهيئة الأولى فقط ويجب إزالته بعد اكتمالها.

4. ثبّت الاعتماديات وشغّل التطبيق:

```bash
bun install --frozen-lockfile
bun run dev
```

5. تحقق من المشروع:

```bash
bun run typecheck
bun run test
bun run build
```

لتشغيل Supabase محلياً وتطبيق جميع الترحيلات من الصفر:

```bash
supabase start
supabase db reset --local
```

## فحوص CI

ملف `.github/workflows/ci.yml` ينفذ:
1. تثبيت الاعتماديات بإصدار القفل.
2. فحص الوحدات الخادمية المعدلة.
3. TypeScript typecheck.
4. الاختبارات.
5. بناء الإنتاج.
6. تشغيل Supabase محلياً وتطبيق جميع الترحيلات على قاعدة نظيفة.

## الملفات المهمة

| المسار | الغرض |
|---|---|
| `src/routes/_authenticated/` | صفحات التطبيق المحمية |
| `src/lib/` | دوال الخادم ومنطق الأعمال |
| `src/integrations/supabase/types.ts` | أنواع قاعدة البيانات |
| `supabase/migrations/` | التغييرات المتسلسلة لقاعدة البيانات |
| `supabase/COMPLETE_DATABASE.sql` | نسخة قاعدة البيانات المجمعة |
| `supabase/MIGRATION_MANIFEST.md` | فهرس الترحيلات |
| `tests/` | اختبارات الأمان والترحيلات |

## تنبيه تشغيلي

لا تعتبر نجاح بناء الواجهة وحده دليلاً على جاهزية النظام للإنتاج. يجب أن تنجح اختبارات CI، وتطبيق جميع الترحيلات على قاعدة نظيفة، ثم اختبار تدفقات تسجيل الدخول والبيع والشراء والمرتجعات والصندوق والصلاحيات بحسابات من مؤسسات وفروع مختلفة قبل فتح النظام للمستخدمين.
